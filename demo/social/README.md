# Social demo

A public comparison demo (relational baseline vs Gleaph graph + vector) built on the
Gleaph platform. The demo graph (`social`) is seeded through the Gleaph CLI, and the
frontend talks directly to the Router canister through `@gleaph/sdk` (prepared queries
by name).

## Layout

| Path               | Purpose                                                                                             |
| ------------------ | --------------------------------------------------------------------------------------------------- |
| `icp.yaml`         | Demo application canister: the frontend asset canister                                              |
| `gleaph.toml`      | Gleaph CLI project config (ADR 0062): `[dirs]`, `[load]`, `[codegen]`                               |
| `migrations/`      | Schema: `SocialGraph` type, typed graph, property indexes                                           |
| `prepared/`        | The six scenario prepared queries (`gleaph prepared apply`)                                         |
| `config/`          | Authored seed data (users, posts, topics, communities, feeds, scenarios)                            |
| `seeds/`           | Generated by `pnpm build:config` (`vertices.jsonl`, `edges.jsonl`, `social-graph.json`); gitignored |
| `src/data/`        | Hand-written wrappers + generated scenario/avatar sources (`src/data/*.generated.*`, gitignored)    |
| `src/generated.ts` | Typed prepared client generated from the Router manifest (`pnpm generate:client`)                   |
| `scripts/`         | Seed generator (`build-config.mjs`), WASM formatter build, avatar generator, `deploy-local.sh`      |
| `src/`             | Solid frontend (connects to the Router through the generated `@gleaph/sdk` client)                  |

## Prerequisites

The Gleaph platform must be running and the `social` graph registered. There are two paths:

1. **Gleaph CLI (dev mode).** Start the local network and deploy the platform canisters
   (Account / Provision), then register an account and provision your Router + graph + shard:

   ```sh
   gleaph network start \
     --account-wasm <account.wasm> --provision-wasm <provision.wasm>
   gleaph signup --name <you>
   gleaph deploy \
     --router-wasm <router.wasm> \
     --graph-index-wasm <graph-index.wasm> \
     --graph-shard-wasm <graph-shard.wasm> \
     --graph social
   ```

   The Router/graph-index/graph-shard wasm artifacts are produced by the repository-root
   `icp.yaml` build (under `target/wasm32-unknown-unknown/release/`). `--graph social` pre-registers
   the `social` graph so the migrations and `gleaph load` resolve it.

2. **Repository operator script.** Deploy the platform canisters and register the `social` graph
   with the deployer as owner (platform bootstrap, then the demo flow below):

   ```sh
   scripts/deploy-demo-local.sh
   ```

   (or deploy `icp.yaml` at the repository root manually and call
   `admin_register_graph` / `admin_register_shard`).

The vector canister wiring (`admin_register_vector_index` etc.) is provisional and handled
separately; the four non-semantic scenarios work without it.

## User flow

With the platform up, run the demo from this directory. The Router principal is
deployment-specific; export it once:

```sh
export GLEAPH_CANISTER=$(icp canister id gleaph-router)   # Router principal
export GLEAPH_IDENTITY=...                                # PEM identity (deployer)
export GLEAPH_NETWORK=$(icp network status local --json | node -e 'const s=JSON.parse(require("node:fs").readFileSync(0,"utf8")); process.stdout.write((s.api_url||s.gateway_url||"").replace(/\/+$/,""))')  # icp-cli managed replica URL
export GLEAPH_FETCH_ROOT_KEY=true                        # required for custom-URL networks
```

(The Gleaph CLI's `local` name points at `http://localhost:8000`, which is not where the
icp-cli managed network listens; `deploy-local.sh` resolves and passes the real URL
automatically, and the manual flow above pins it through `GLEAPH_NETWORK`.)

If you provisioned the Router through `gleaph deploy` (dev mode, above), the Router principal is
already written to the per-environment Router cache (`.gleaph/cache/account/<env>.router.json`), so
`gleaph migration apply` / `gleaph load` / `gleaph prepared apply` resolve it automatically and
`GLEAPH_CANISTER` is not required. When the platform was deployed by `scripts/deploy-demo-local.sh`
instead, export `GLEAPH_CANISTER` as shown.

Then the whole demo is six commands:

```sh
pnpm build:config                    # 1. regenerate seeds/ and generated sources
pnpm generate:avatars                # 1b. (re)fetch scaled avatars from DiceBear if missing
                                     #     (the 140 default avatars are committed, so this is a no-op)
gleaph migration apply               # 2. schema: graph type, typed graph, indexes
gleaph load seeds/vertices.jsonl seeds/edges.jsonl   # 3. seed data (gleaph.toml pins graph/key/state)
gleaph prepared apply                # 4. register the six scenario queries
pnpm generate:client                 # 5. regenerate the typed client from the Router manifest
icp deploy                           # 6. deploy the frontend asset canister (this icp.yaml)
```

`scripts/deploy-local.sh` runs exactly these steps (starting with `pnpm build:config`,
plus the frontend build and writing `.env.local` so the build bakes in the Router
principal). When the platform is not running (network down or Router missing), it
automatically delegates to the full bootstrap `scripts/deploy-demo-local.sh` first;
set `GLEAPH_DEMO_SKIP_AUTO_BOOTSTRAP=1` to fail with guidance instead. A non-default
`GLEAPH_DEMO_INSTALL_MODE` (e.g. `reinstall`) also delegates, so the platform canisters
are (re)installed even when the platform already looks ready:

```sh
./scripts/deploy-local.sh
```

Then serve the frontend:

```sh
pnpm install
pnpm dev                  # reads .env.local for the Router id and local host
```

`deploy-local.sh` also verifies the demo's own managed local network (the one hosting the
asset canister, per `demo/social/icp.yaml`) before deploying. `icp network status` trusts
its cached descriptor, which can point at a stopped or removed container after a
Docker/OrbStack restart or after macOS cleans the network's temp status dir; when the
replica does not answer, the script recreates the network automatically (which also clears
the stale canister mapping, so the asset canister is deployed from scratch). Set
`GLEAPH_DEMO_SKIP_NETWORK_START=1` to fail with guidance instead of auto-starting.

`pnpm install` links `@gleaph/sdk` from the workspace. Its `dist/` is gitignored,
so run `pnpm sdk:build` (or the repository-wide `pnpm install:all`) once before the
first build if `sdk/client/js/dist` is missing.

## Regenerating seeds and generated sources

The seed artifacts (`seeds/`) and generated sources (`src/data/*.generated.*`) are
produced by the seed generator and are gitignored; run `pnpm build:config` before the
CLI user flow (the `check`/`build` scripts and `deploy-local.sh` do this
automatically). After changing `config/` or `prepared/`, regenerate and validate:

```sh
pnpm build:config                       # node scripts/build-config.mjs
node --test scripts/build-config.contract.test.mjs
```

The scenario `preparedQueryId` selects the `prepared/<preparedQueryId>.gql` source
that `gleaph prepared apply` registers and that the generator embeds into
`src/data/scenarios.generated.*`. The frontend calls the typed prepared methods
from `src/generated.ts` (`client.publicTimeline({ offset })`, `client.semanticDiscovery({ offset, query })`, ...);
the semantic scenarios pass their fixed query vector as a `Bytes` parameter.

Avatar SVGs for the 140 authored/scaled users are committed under `public/avatars/`.
`pnpm generate:avatars` regenerates them from DiceBear only when a changed user
scale (`SOCIAL_DEMO_USER_SCALE`/`SOCIAL_DEMO_POST_SCALE`) leaves some missing;
with the default scale it is a no-op, so offline builds still show every avatar.

### Regenerating the typed client

`src/generated.ts` is produced by `gleaph-codegen` from the prepared manifest
served by the Router. It is committed so the frontend builds without a running
Router; after changing `prepared/`, `gleaph prepared apply` re-registers the
queries and then the client must be regenerated from the live manifest:

```sh
pnpm generate:client                   # gleaph codegen (fetches the Router manifest)
node --test scripts/build-config.contract.test.mjs
```

The Router derives each operation's parameters and result columns when it
registers the query (`prepared/*.gql`); `gleaph codegen` reads that manifest and
writes `src/generated.ts`. `[codegen]` in `gleaph.toml` pins graph/target/output
and the canister comes from `GLEAPH_CANISTER` (exported in the user flow above)
or `--canister`. The generated code encodes each parameter by its manifest type
and decodes rows with the SDK's `decodeRows`.

## GQL formatter WASM

The query panel uses the formatter owned by `gleaph-gql` through the thin adapter in
`wasm/`. Regenerate the browser bindings after changing the adapter or formatter API:

```sh
pnpm run build:gql-formatter
```

## UI localization

The UI uses `@solid-primitives/i18n` with static English and Japanese dictionaries.
The language selector is in the top bar and remembers the selected locale in browser
storage. UI labels, explanations, query annotations, status messages, and relative-date
labels are localized; post bodies and account names remain the scenario's original
content.
